# Checkout, PayAssure, Webhook, and Database Flow

This document describes the checkout and payment lifecycle implemented in this
repository: what happens before the checkout response, what happens when
PayAssure sends a webhook, how state is persisted, which work is asynchronous
from the user's point of view, and where delays can occur.

The description follows the current application code. It does not assume that
PayAssure's internal payment processing is synchronous or that a webhook will
arrive within a particular time.

## At a glance

```text
POS browser
  1. Opens authenticated checkout-status event stream
  2. POSTs checkout
       |
       v
POS server
  3. Validates request and stages pending sale + items + settlement in PostgreSQL
  4. Releases staging transaction/connection
  5. Authenticates retailer with PayAssure
  6. Initiates settlement with PayAssure
  7. Saves provider identifiers/status and returns checkout acknowledgement
       |
       +---- browser keeps waiting on the event stream ----+
       |                                                   |
       v                                                   |
PayAssure sends webhook                                    |
  8. POS verifies signature and parses event                |
  9. In a PostgreSQL transaction, deduplicates event,       |
     applies sale/settlement/inventory updates, and commits |
 10. Publishes PostgreSQL status notification -------------+
                                                           |
Browser receives terminal status, updates UI and refreshes |
POS data/dashboard                                         |
```

The checkout POST response means that the POS has received PayAssure's
settlement-initiation response and refreshed its local status. It does not, by
itself, mean that collection and settlement have completed. The browser
continues waiting for a terminal state delivered through the status event
stream.

## 1. Browser starts checkout

The checkout UI uses `useCheckout` and `checkoutApi`:

1. The browser clears prior notices/errors and enters its initiating state.
2. It creates or reuses a merchant transaction reference. The reference is
   stored in `sessionStorage` to support recovery/retry after interruption.
3. Before sending the checkout POST, it opens an authenticated
   `EventSource` at `/api/checkout/:reference/events` and waits for the stream's
   `open` event. This ordering is intended to avoid missing a fast webhook
   update.
4. It then POSTs `/api/checkout` with the payment method, reference, items,
   and applicable payer/phone fields.
5. After the POST response, it waits for a terminal status on the event stream
   if the returned sale status is still `pending`.
6. On terminal success it clears the cart and reference. On terminal failure
   it shows the settlement error (or a fallback message). In either case it
   refreshes POS data and the dashboard in the background.

The event stream first issues `LISTEN` on the PostgreSQL checkout-status
channel, then reads the current status. On matching notifications it queries
the current database state and writes a `checkout-status` SSE event. If the
sale is already terminal, the server ends the stream. The stream holds a
dedicated PostgreSQL pool client until it closes.

The browser's overall checkout experience therefore includes two separate
waits:

- **Initiation wait:** the checkout POST, through local staging and PayAssure's
  initiation response.
- **Completion wait:** after the POST response, until a terminal webhook-driven
  state reaches the event stream.

The current browser status wait has no application-level terminal timeout or
polling fallback. A delayed/missing webhook, or a status-stream problem after
the stream opens, can leave the UI waiting.

## 2. Checkout POST: synchronous work before acknowledgement

The route is authenticated and then calls `handleCheckout`. The following
operations are awaited as part of handling the POST, and normally complete
before the server sends the checkout response.

### 2.1 Validation and reference handling

- The request is validated against the checkout schema.
- Item quantities are combined by product ID and checked for safe bounds.
- For M-Pesa, the phone number is normalized/validated.
- A reference is taken from the request or generated by the server.
- A request fingerprint is computed for the staged settlement.
- The server obtains a PostgreSQL pool client.

Invalid input returns a 400 response. Authentication/session lookup and pool
client acquisition also occur on the request path.

### 2.2 Stage the pending sale and reserve inventory

The server begins a PostgreSQL transaction and:

1. Takes an advisory transaction lock for the merchant transaction reference.
2. Checks whether the reference already exists. If it does, it generates a
   fresh server reference.
3. Locks product rows in sorted product-ID order.
4. Checks available product stock, accounting for quantities on other pending
   sales.
5. Locks eligible unexpired batch rows and allocates stock by expiry date,
   accounting for pending-sale reservations.
6. Calculates the sale total.
7. Inserts the `sales` row with `status = 'pending'`.
8. Inserts `sale_items` rows with prices and batch/supplier details.
9. Builds and stores the PayAssure settlement payload and settlement record.
10. Prepares/validates the settlement payload, including supplier/retailer
    amounts and buying-price requirements.
11. Commits the transaction.

The pending sale and items are therefore persisted before a request is made to
PayAssure. Pending sales reserve stock for availability calculations; inventory
counts themselves are decremented when a successful collection webhook is
applied.

The checkout transaction ends before the outbound PayAssure request. The
database connection used for staging is released before settlement initiation,
so product/batch row locks are not held while waiting for PayAssure.

If staging fails, the transaction is rolled back. Where applicable, a failed
checkout attempt is written to `failed_checkout_attempts` before the error
response is sent.

### 2.3 Initiate settlement with PayAssure

After staging, the server:

1. Marks the PayAssure request as started.
2. Saves the prepared payload into `payassure_settlements`.
3. Obtains the current PayAssure platform session. If the stored session is
   missing or cannot be decrypted, the code refreshes/logs in and stores new
   tokens.
4. Calls PayAssure retailer authentication at
   `/settlement/authenticate`.
5. Calls PayAssure `/settlement/initiate-settlement` with the prepared
   settlement payload and retailer session token.
6. Reads and validates the provider response and extracts request/settlement
   identifiers when present.
7. Updates the local settlement row (for example, `accepted` when it is still
   `queued`) and saves provider identifiers.
8. Queries the sale and settlement status again.
9. Sends the checkout response: HTTP 202 while the sale is pending, otherwise
   HTTP 200.

The checkout payload uses `MPESA` with the normalized phone for M-Pesa
checkouts. Other payment methods use the `CASH` payment method in the
PayAssure payload. The sale's payment method is separately stored on the sale
record.

The retailer-authentication request and settlement-initiation request are
sequential. The settlement request helper sets a 15-second abort timeout for
each outbound request. A session refresh/login can add another outbound
request if required. These timeouts apply to individual requests, not a single
overall checkout deadline, so total time can exceed 15 seconds.

If PayAssure rejects initiation, the server stores failure information and
returns an error response (normally 502 from the checkout error handler). A
definitive provider 4xx rejection marks collection and sale failed; an
ambiguous/non-4xx initiation failure leaves collection pending to avoid
incorrectly treating an uncertain provider outcome as a definite failure.
If PayAssure accepted initiation but the POS cannot refresh local status, the
server returns an explicit 500 and warns the client not to retry blindly.

### 2.4 Work after the checkout response is sent

If the initiation response contains a provider settlement ID, the handler
checks for webhook events previously received before the local settlement
mapping existed and attempts to apply them. This deferred-event processing is
awaited by the handler after it has sent the HTTP response. It can therefore
continue consuming server/database resources after the client has received
the acknowledgement, but it does not extend the already-sent response.
Failures in this follow-up are logged.

## 3. PayAssure webhook: validation and persistence

The server accepts webhook requests at `/webhook`. The application configures
this path to read a raw JSON body, which is needed for signature verification.
The webhook route handles the following before acknowledging the provider:

1. Requires a raw JSON body and reads the recipient merchant ID.
2. Loads the recipient's webhook secret. A cached secret avoids a database
   read; otherwise the server reads the encrypted credential from PostgreSQL.
   If it is unavailable/unreadable, the code can fetch PayAssure participant
   details and save the secret for later use.
3. Checks the signature and timestamp against the raw body (the accepted
   timestamp window is five minutes).
4. Parses and validates the webhook event.
5. Obtains a PostgreSQL client and starts a transaction.
6. Inserts the webhook event into `payassure_webhook_events`. The provider event
   ID is unique per recipient merchant.
7. Applies the event to the matched settlement/sale and associated inventory.
8. Marks the webhook record processed and commits the transaction.
9. Publishes a PostgreSQL notification for the checkout status stream.
10. Returns HTTP 200 to PayAssure.

The webhook acknowledgement follows the database commit, so the primary event
record and state changes are committed before a normal success response. The
checkout notification is attempted after commit and before the route sends its
200 response. Notification errors are logged, but do not roll back committed
payment state.

### 3.1 Event idempotency and mapping

- A repeated `(recipient_merchant_id, provider_event_id)` is treated as a
  duplicate. It is committed/ignored and acknowledged with HTTP 200.
- Normal settlement events are matched first by merchant transaction
  reference, then by provider settlement ID, and then by a child settlement
  reference associated with a parent checkout.
- Currency and amount are checked against the checkout. Child settlements
  have a bounded positive amount check; a top-level settlement must match the
  checkout total.
- Settlement event timestamps are checked so an older event cannot overwrite
  newer settlement state.
- If no local checkout mapping exists yet, the signed webhook is persisted
  with its event payload and error message, committed, and acknowledged with
  HTTP 202 (`pending: true`). It remains available for deferred processing
  after settlement initiation establishes the local mapping.
- Other mapping conflicts or amount/currency mismatches return 404/409 as
  applicable. Invalid body/signature/recipient requests are rejected before
  inserting a webhook event.

### 3.2 State and inventory changes

The primary records involved are:

- `sales`: sale status, payment method, total, payer details, creation time.
- `sale_items`: products, quantities, captured prices, supplier/buying-price
  data, and allocated batch information.
- `payassure_settlements`: merchant reference, stored request payload,
  collection/settlement statuses, provider identifiers, last event and error.
- `payassure_webhook_events`: received event payload, event ID/type,
  processing status, timestamps, and error.
- `failed_checkout_attempts`: failed attempt reason and relevant checkout
  details.
- `product_batches` and `products`: inventory quantities.

Collection and settlement are distinct parts of completion:

- `payment.collection.succeeded` confirms collection, decrements batch and
  product inventory in the webhook transaction, and records the collection
  status. The sale is completed only when settlement status is also completed.
- `payment.collection.failed` marks collection and the pending sale failed and
  records the failure.
- Settlement-start/progress/retry/reconciliation events update settlement
  status and event details.
- A completed settlement marks the sale completed only if collection has
  succeeded. If settlement completes first, the sale remains pending until
  collection succeeds.
- A partially failed settlement marks the sale failed and records a failed
  attempt.

### 3.3 Status notification to the POS

After a webhook transaction commits, the server publishes the checkout
reference on PostgreSQL's `payassure_checkout_status` notification channel.
The SSE route listens for that notification, re-reads current status from the
database, and sends the current state to the browser. The notification itself
is a signal to re-query; the database remains the source of truth.

## 4. Synchronous versus asynchronous activities

Here, **synchronous** means awaited on a request/response path or otherwise
required before the user/provider receives that response. It does not mean
that JavaScript runs synchronously on one thread.

| Activity | When it happens | Does it delay an HTTP response? |
|---|---|---|
| Browser opens checkout SSE and waits for `open` | Before checkout POST | Delays starting the POST and therefore delays the user's overall checkout |
| Checkout validation, pool acquisition, locks, stock checks, DB writes and commit | Checkout POST | Yes |
| PayAssure retailer auth and settlement initiation | Checkout POST | Yes |
| Final local settlement update and status query | Checkout POST | Yes |
| Deferred webhook processing for an early event | After checkout JSON is sent | No, but it uses server/database resources |
| PayAssure's later collection/settlement processing | After initiation | Not the already-returned POST; it delays final user completion |
| Webhook signature verification and event parsing | Webhook POST | Yes, delays webhook acknowledgement |
| Webhook event insertion, matching, state/inventory writes and commit | Webhook POST | Yes, delays webhook acknowledgement |
| Checkout `pg_notify` query after webhook commit | Webhook POST | Yes, because it is awaited before the 200 response |
| Browser receives SSE update and refreshes data/dashboard | After webhook notification | Does not delay checkout POST; delays when the UI reflects/refetches final state |

## 5. Causes of a slow checkout response or a slow final result

These are code-path and infrastructure risks, not claims that a particular
delay is currently occurring.

### Delays before the checkout POST is sent

- The browser waits for the authenticated SSE connection to open before
  initiating the POST.
- A slow session store/database connection or network can delay that stream
  setup.

### Delays in the checkout POST response

- **PostgreSQL pool/client acquisition:** the handler must obtain a client.
  Pool saturation, slow database connectivity, or a database restart can make
  this wait or fail.
- **Persistent status-stream clients:** each open checkout SSE stream holds a
  database client. The pool is created without explicit pool sizing in this
  code. Many simultaneous open streams can contribute to pool pressure and
  delay checkout, webhook, and status-query work.
- **Database lock waits:** the staging transaction locks product and batch
  rows and takes a reference advisory lock. Concurrent checkouts for the same
  products/batches or reference can wait for another transaction.
- **Database query/commit time:** staging performs multiple awaited queries;
  larger carts mean more rows and work. Slow storage, missing/ineffective
  indexes, database load, or lock contention can add latency.
- **Payload preparation:** settlement lines and stored sale details are read
  and validated before the provider call. Missing buying prices or invalid
  amount relationships cause a failure response rather than a successful
  initiation.
- **Sequential PayAssure network calls:** retailer authentication completes
  before settlement initiation starts. DNS, connection establishment, TLS,
  provider load, network latency, and provider response/body time all add to
  the response time.
- **Per-request timeout accumulation:** the two settlement calls each have a
  15-second timeout. A failure near timeout on each call can make the total
  much longer than 15 seconds. Session refresh/login may add further time
  when the stored platform session is unavailable or rejected.
- **Provider response parsing and final DB round trips:** reading/parsing the
  provider response, saving provider identifiers, and querying the final
  status are all on the checkout POST path.
- **Failure bookkeeping:** on rejected or failed checkouts, rollback and
  recording a failed attempt/status can also add database work before the
  error response.

### Delays between acknowledgement and final checkout status

- PayAssure may take time to collect payment or complete settlement after
  accepting initiation; that work is outside the POS checkout POST.
- Delivery timing/retries of the provider webhook affect when the POS learns
  the outcome.
- A webhook arriving before the local settlement mapping is committed is
  stored as deferred and then applied in the post-acknowledgement deferred
  processing path.
- Webhook validation can require a database lookup for the signing secret. On
  a cache miss without a stored credential, it can also require a PayAssure
  participant API request (and potentially platform-session refresh).
- Webhook processing includes event mapping, row locks, inventory validation
  and updates, event persistence, and commit. Database load or lock waits can
  delay its acknowledgement and the status notification.
- The checkout status route depends on the PostgreSQL notification listener
  and a fresh status query. Stream interruption or a missing/delayed
  notification may delay the browser's final update. The UI currently has no
  application-level wait timeout or polling fallback.
- After final status arrives, POS data/dashboard refresh is separately
  asynchronous and may take additional time. Refresh failure is logged and
  does not reverse a successful checkout.

## 6. Useful code locations and operational signals

- Browser orchestration: `web/src/app/useCheckout.ts` and
  `web/src/app/checkoutApi.ts`.
- Checkout route and staging: `server/src/routes/post-api-checkout.ts`,
  `server/src/services/checkout-controller.ts`, and
  `server/src/services/checkout-staging.ts`.
- Provider calls: `server/src/payassure-settlement.ts`,
  `server/src/payassure-settlement-auth.ts`, and
  `server/src/payassure-settlement-request.ts`.
- Webhook route/verification/transaction: `server/src/routes/post-webhook.ts`,
  `server/src/services/webhook-verification.ts`, and
  `server/src/services/webhook-transaction.ts`.
- Webhook event application and inventory: `server/src/services/webhook-event.ts`,
  `server/src/services/webhook-event-stock.ts`,
  `server/src/services/webhook-event-settlement.ts`, and
  `server/src/services/webhook-event-failure.ts`.
- Status event stream: `server/src/routes/get-api-checkout-reference-status.ts`
  and `server/src/services/checkout-status-events.ts`.
- Table definitions and incremental schema changes: `server/schema/`.

The application logs include checkout references, sale IDs, provider request
and settlement IDs, event IDs/types, state transitions, and selected failure
details. Correlate checkout logs by merchant transaction reference and webhook
logs by provider event ID/settlement ID. The code redacts provider credentials
from relevant request/error logging; do not put credentials or raw secrets in
support notes.
